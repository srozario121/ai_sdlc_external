## Context

On 2026-10-04 the user asked for an interactive HTML report to compare
benchmark and held-out runs across versions. The report has a summary tab,
trace-level tabs, and a section on areas of improvement written by the agent
that generates the report. It is stored in a git-ignored scratch folder, and
its link is printed at the end of every run.

The investigation of held-out `-11` the same day showed that a useful trace
comparison needs content: the turn where reasoning ran away, the tool call
that was running at the kill, and the patch at the cap against the one the
agent intended. For a held-out instance, that content derives from the
instance. ADR 0016 lets only ids, hashes, counts and aggregates into the
repository. Item 42's replay store goes further and refuses any path inside a
git checkout.

Four questions cross items, so they are settled once here. Every benchmark
driver (`run.sh`, `paired-campaign.py`, `pro-campaign.py`, the coding bench)
will hook the report in.

1. Where can such a file live, and how is it kept out of git?
2. Who may see it?
3. What may the generated "areas of improvement" text do?
4. Can the hook disturb a timed run?
5. What may leave the box when a model off the box writes the narrative?

## Decision

1. **The report is a local artefact.** It is written under the main
   checkout's `results/reports/`, which `.gitignore` already covers through
   `results/`, and is resolved from any worktree the same way ADR 0014
   resolves `.env`. Before writing, the generator checks with
   `git check-ignore` that the target is ignored. If it is not, the
   generator refuses (exit 3).
2. **It has two content tiers.** `ids` holds instance ids, counts,
   aggregates, tool names, durations and repository file paths. It is safe to
   quote anywhere ADR 0016 allows. `local` adds bounded snippets: reasoning,
   tool arguments and output, and patch hunks, each capped. A `local` report
   carries a banner and a marker (`<meta name="aisdlc-report"
   content="local-only">`), and `make check` fails if any tracked file carries
   that marker.
3. **A report is never published without the user's explicit say-so.** This
   covers a claude.ai Artifact, a PR or issue attachment, a gist, a Langfuse
   upload, or a committed copy. A record that cites a report quotes its
   `ids`-tier numbers only.
4. **The HTML is self-contained.** It has inline JS, CSS and SVG, and no
   network fetch at runtime. A Content-Security-Policy of `default-src
   'none'` enforces this.
5. **The areas of improvement are advice, never a decision.** A
   deterministic rules engine produces the findings, and each one cites
   instance ids and metric values. An optional narrative is written by
   **Claude** on demand (`NARRATE=claude`). It is labelled "generated by
   Claude (<model>), unreviewed", and uncited claims are dropped. It cannot
   alter a metric, a verdict, a pin or a backlog item. Only a person turns a
   finding into a change.
6. **Only ids and aggregates leave the box.** The narrative sends Claude a
   payload built from a committed **whitelist schema**:
   - instance ids that match the id pattern;
   - arm labels;
   - enumerated stage, rule-id and tool-kind values;
   - numbers and booleans;
   - the rule findings, in that vocabulary.

   It never sends free text, a file path, a snippet, reasoning, a tool
   argument or its output, or a patch, **at any content tier**. Sending
   held-out content off the box would break ADR 0016, whose rule 3 lists
   ids, hashes, counts and aggregates as everything that may cross. A
   payload that fails validation is refused, and the call is not made. A
   selftest plants canary strings in every content field of its fixtures
   and proves none reaches the call. The exact payload is kept beside the
   narrative for audit.
7. **The narrative is invoked through the user's own Claude Code login.**
   - The command is `claude -p --output-format json --tools ""
     --strict-mcp-config --no-session-persistence`, run from an empty
     temporary directory with the payload on stdin.
   - The generator never reads `.env` and never reads, sets or prints a key
     or token.
   - It never uses `--bare`, which needs an API key, or a permission
     bypass.
   - When `claude` is missing or not logged in, it skips cleanly.
8. **The hook never disturbs a run.** At the end of a run it builds only the
   deterministic report, under a time bound. It never changes the run's exit
   code. It makes no call to the serving engine, and it never sends
   anything off the box: the narrative runs on demand only.
9. **The report reads, it does not rule.** The paired counts and exact
   intervals it shows are labelled descriptive. A pre-registered verdict
   appears only when its own analyser's output file is passed in, and the
   report displays it verbatim (ADR 0011 §3).

## Consequences

- Held-out content can be inspected side by side on the box, and the public
  repository still receives only ids and aggregates.
- A worktree's own `results/` is never the home of a report, because it is
  deleted with the worktree.
- The marker scan is one more `make check` assertion, cheap and offline.
- An end-of-run report has no narrative unless the user asks for one, so
  no run sends data off the box by default.
- The narrative reasons over numbers and findings only. It cannot quote a
  trace, so its advice is only as specific as the rules and aggregates
  make it. That is the price of keeping held-out content on the box.
- The whitelist is a closed vocabulary. A new attribute reaches the
  narrative only when the schema is amended, and the canary selftest keeps
  free text out.
- The user chose the `local` tier inside the ignored `results/` over ADR
  0016's stricter reading (refused inside any checkout, written to
  `~/.cache/ai-sdlc-reports/`). If that changes, rule 2 changes in one
  place.

## Delivery notes (item 66 PR 3, 2026-10-04)

The user's review (T12) added two things. Neither changes a rule above.

- **A rule-based recommendation, which rule 9 bounds.**
  - The Summary shows a PASS / FAIL / INCONCLUSIVE card per arm, from a
    committed table (`scripts/report/recommend.tsv`).
  - It is labelled "recommendation (rule-based), not a pre-registered
    verdict".
  - A `VERDICT=` analyser file is shown beside it, verbatim, and is the one
    that counts.
  - Like the findings (rule 5), it never changes a pin or an item.
  - By the user's decision (2026-10-04), contended runs that are excluded
    from scoring do not make a card INCONCLUSIVE. The card lists them as
    information.
- **Rule 6's whitelist widens, by enumerations and numbers only.**
  - The payload adds each arm's recommendation (an outcome enumeration and
    rule-id enumerations), the cost fields, the unpriced reasons and the
    findings' impact.
  - It carries no text, path or content.
  - The prompt tells the narrative the recommendation is fixed.
- **One HTML detail of rule 4.** An SVG `clip-path` refers to its own
  `clipPath` as `url(#…)`. That is a same-document fragment, not a fetch,
  and the selftest allows `url(#` and nothing else.
